The constraint everything sits under

Gate B is unresolved

No real child may use this build

Every scientific parameter in the running system is an engineering placeholder, not an approved value: the BKT configuration, the certification threshold θ_B, the sequencing policy, the five-question session bound, the absent attempt limit, and the timeout policy. Work proceeds against TEST-provenance DRAFT bundles only. No pilot, no classroom, no production use is authorised until Gate B closes.

This is not a formality that slows the build down — it is what makes the build safe to do at speed. Because no child is exposed, engineering can move fast and defer policy questions honestly, provided every deferral is written down rather than assumed.

Two consequences shape the plan below. First, anything that depends on a governed number cannot be finished now, only prepared. Second, deferrals must be tied to Gate B itself — never to “user testing”, which Gate B currently prohibits, and which would make the trigger condition unreachable.

Deliberately does not disable input on expiry — doing so would soft-lock the session, because advancing requires at least one recorded attempt and no server-side sweep exists. The invariant is held by an exported function with a failing test attached, not a comment.

Phase 3 · Learner loop

In sequence

Three batches, strictly ordered. Each depends on the one before it, because the completion response is what drives the next question.

FE-3d Hints Next

409 is the normal response, not the error path. Only two of thirty-six templates carry hint content, so roughly 94% of requests for help find none. The plumbing is trivial; the copy is the hard part — “no hints available” reads as a rebuff to a child who just asked for help. The client must not try to distinguish “exhausted” from “never had any”: both are 409, and the distinction does not exist server-side.

Depends FE-3b Test template B-CNT01-SEQ-CONTINUE Exit graceful 409 on any other template
FE-3e Advance and completion loop Queued

The completion response drives everything: when it carries the next question, render it directly rather than asking again. Progress counts come from the response — never a client-side counter, never a constant. Requires at least one recorded attempt, so the button gates on having submitted.

Depends FE-3d Exit five-question run, resumable at every step
FE-3f Results screen Queued

Counts only. No score, no percentage, no stars, no streak, no mastery. The client observes every outcome during a session and must not accumulate them — doing so would synthesise exactly the evaluative summary the backend deliberately withholds. That prohibition needs a code comment, or a reviewer will “fix” the apparent omission.

Depends FE-3e Known quirk summary reports abandoned as active

Backend · research integrity

Measurement corrections

The system records the opposite of what the taxonomy defines

The specification defines timeout_no_response as response time over cap, no submit. The implementation only ever writes that class when a child did submit — and then discards their answer unread. A child who genuinely never answers produces no row at all, because nothing sweeps expired questions. Every row in the class is a false positive by the specification's own definition, and the true cases are structurally invisible.

The five-minute cap itself is not the problem. Against the study's own response-time model it sits roughly eight standard deviations out even for the dyscalculic cohort, so it never binds on processing speed. It is a disengagement threshold wearing a latency threshold's clothes.

BE-M1 Flag, never discard Highest priority

Always persist the submitted value and always evaluate the match, then attach a deadline_exceeded flag and server-measured latency. Every current behaviour stays reproducible by filtering on the flag. This is the only irreversible item on the plan — a timeout flag can be re-derived from timestamps forever, but a discarded answer is gone.

Blocks BE-M2Reversibility none once data is collected
BE-M2 Split late response from non-response Queued

Two different phenomena with different psychological readings currently share one label. Only the second matches the taxonomy. They must not be merged in the error-class distribution, whose marginals are already calibration-pending.

BE-M3 Make true non-response observable Queued

Requires either a sweep or inference at session completion. Until then the class the taxonomy actually defines has a structurally zero base rate — a silent, total measurement gap rather than a small bias.

BE-M4 Derive the cap from a stated construct Gate B

The specification never numerically defines the cap; five minutes is an engineering round number. Gate B should state which construct the cap measures — disengagement, not latency — and justify a value against it.

What is already protected

Mastery estimation is clean: the update is gated on a first attempt that is a real response, so timeouts never become observations, and certification depends only on that estimate and the guess-guard. Response-time aggregates already exclude timeouts. The damage is confined to the descriptive layer — first-attempt accuracy and the error-class distribution — not the adaptive engine.

How batches are run

Standing rules

  1. One bounded batch at a time. Named file scope, explicit non-goals, independently verifiable. A batch that grows mid-flight is two batches.
  2. The client renders, the server decides. No correctness, mastery, sequencing, hint policy or attempt limit is ever computed client-side. Failing closed is always preferred to guessing.
  3. Verify against the compiler, not the editor. Diagnostics lag edits; tsc, lint and the test run are the record.
  4. Append to buildLog1.md, never edit it. Record findings and rejected options, not just diffs — the reasoning is what survives.
  5. Report coverage honestly. “Unit-tested, not verified live” is a useful sentence. Implied coverage is a defect.
  6. Defer to milestones that will occur. Tie every deferral to Gate B, never to evidence current governance forbids collecting.
  7. No agent mutates git. Work is left staged for review; commit messages carry no AI attribution.
